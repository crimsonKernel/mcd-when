# 进阶：批量核价与「按需单城查询」

`README.md` 里的主流程是 `survey_national.py`（探针抽样，快）。这一页讲另外两种跑法。

## 三层架构：为什么不需要反复重跑全国

| 层 | 由谁跑 | 目的 | 刷新频率 |
|---|---|---|---|
| **388 城快照** | 一次性批量采完，落在 `data/surface_national.json` | 传播、榜单、离线报告 | 参赛提交前定稿 |
| **按需单城查询** | 用户问哪个城市就现跑哪个城市 | 答案永远新鲜 | 每次提问实时 |
| **缓存累积** | 查过的城市写回同一份 JSON | 第二次同城市直接命中 | 自动 |

价格是会变的（门店调价、上新），所以「全国快照 + 按需实时」比「反复全国重跑」更合理。

## survey_batch.py：一次调用拿全菜单

关键事实（真机验证）：`calculate-price` 的 `items` 数组可以一次传多件，
返回的 `productList` 里带**每件商品的名称与单价**——不必再抽样。

```bash
# 单城全菜单采集(约 1~2 分钟)
python src/survey_batch.py --city 苏州

# 多城并发
python src/survey_batch.py --city 上海 --city 北京 --workers 6
```

实测（2026-10-21）：单城拿到 336~458 个商品，0 失败。

**为什么比探针版准**：探针版每档只问 20 件商品，上海午餐地板价是 ¥14.90；
全菜单版扫完所有商品后是 **¥13.90（精选超值随心配）**——漏掉的更便宜选项被找了回来。

### 两个坑

1. **整批传太多会失败**：一次塞 123 个返回错误，分块 25 稳
2. **混进不可售商品整批失败**：返回「商品已售罄或不可售」，脚本用**二分降级**救回好的那半边
   ——这也是为什么实测约 400 次调用/城，而不是理想的分块数

因此批量版**不适合全国一次性重跑**（388 城 × ~400 次 ≈ 15 万次调用），
它更适合按需单城查询：贵一点点，但答案是完整的。

## 找不到自己的城市？

两种情况：

1. **城市在列表里但采集失败** → 多半是该城所有门店都不支持预约取餐（接口返回 600056），
   探测时会记录候选门店逐个试；真的全城不支持就只能跳过
2. **城市压根不在列表里** → 加进 `src/cities_cn.py`，见 `CONTRIBUTING.md`
